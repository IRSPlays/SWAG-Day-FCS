# Taste
- Wants the agent to fully understand a project (architecture, configs, source tree) before performing actions — opens sessions with broad "read and UNDERSTAND THIS PROJECT" style requests and expects a self-directed deep-dive (docs, structure, git status/diff of uncommitted work) followed by a concise, complete summary. Confidence: 0.8
- Maintains a HANDOFF.md in the project root as the canonical cross-session context doc (project purpose, architecture mechanics, machine quirks, current uncommitted-work state) and explicitly points the agent at it (@HANDOFF.md) when onboarding — read it first and treat it as authoritative. Confidence: 0.8
- Gives terse, informal one-line commands for large multi-step tasks (clone a repo, install deps, swap the entire color palette) and delegates end-to-end — expects the agent to plan, execute, make sensible context-dependent judgment calls on details, verify (build + smoke test), and summarize results without asking clarifying questions. Confidence: 0.7
- Does their own visual QA and reports back informally — usually attaching a screenshot of the offending frame for visual bugs — sometimes retracting an issue once they recheck ("nvm the images background works") — re-confirm a reported issue still reproduces before investing in a fix. Confidence: 0.6
- In the SWAG Day FCS stage app, the user's intent is a white background app-wide — including the /stage page, the ScaledFrame letterbox, and all non-performance slides (they explicitly rejected a dark/grey stage: "the /stage is still using the grey backgrounnd, use the white"); dark is reserved only for the lyric/performance slides themselves (LyricsMograph output). Confidence: 0.85
- Ambient/background visuals should be soft, premium, and MOVING, staying tasteful on the white stage. Gradients ARE allowed but only when they read as physical lighting (vignettes, light falloff, motion falloff) — never AI-looking mesh-gradient blobs or generic purple-blue washes (their earlier mesh-gradient-drift pick is superseded by this rule). The current agreed direction for SWAG Day FCS is AmbientBackground v4 "halftime field": canvas dot grid + random luminance crest + twinkle + projector vignette. Confidence: 0.85
- Backgrounds/animations must FEEL ALIVE: pair a dynamic layer driven by randomness (random paths, randomized timings — so nothing ever loops identically) with a passive ambient layer (slow, unsynchronized micro-motion like spark twinkles). Explicitly demanded "DYNAMIC AND PASSIVE ANIMATIONS... HIGH QUALITY... FEELS ALIVE"; fixed mechanical loops were rejected as too static. Confidence: 0.8
- Declines interactive multiple-choice pickers: asked for background options plus "SURPRISE ME", then declined to pick when shown 4 concept directions — present options briefly, but proceed autonomously with the boldest best-judgment direction rather than blocking on a choice (the autonomous pick was accepted without pushback). Confidence: 0.7
- Attaches source-of-truth documents for content re-plans (the EMCEE script .docx defines the show flow for the slide deck; a video-submission .xlsx + YouTube links map performers to songs) and expects the agent to extract them itself — unzip OOXML and parse document.xml / sharedStrings.xml, fetch YouTube titles via oEmbed — and reconcile against the current code before proposing the new plan, flagging unconfirmed items (TBC) explicitly instead of guessing. Confidence: 0.7
- Show-control UX must be radically simple: ONE key (→ / Space) drives the entire show — the active slide claims the advance first (word-by-word lyric stepping for live bands, track start for backed songs, answer reveals in game slides), otherwise the deck cues next. Any new slide or interactive feature must plug into this advance protocol (`useSlideAction` / `advance` event) rather than adding its own controls. Confidence: 0.85
- The operator console is a MUTED monitor: /controller mirrors the stage as a synced preview but must never emit audio (the stage machine owns the PA), with a stripped control set — advance/back, blackout, cam cuts, timer. Confidence: 0.85
- All UI must be distinctive and hand-authored, never generic-AI-looking — applies beyond backgrounds to whole pages/consoles ("the UI HAS TO BE UNIQUE, NOT AI and SUPER GOOD, SUPRISE ME"). Bold single-concept themes (jumbotron halftime field, drag-race "Start Tree" cue console) are the accepted register. Confidence: 0.8
- Close large builds with an explicit "what you need to provide" list — exact songs to download, photos, and confirmations — since the user asks "tell me if I need to download any songs" / "is that all u need" and wants a definitive asset/input checklist, not open-ended offers. Confidence: 0.6
- ALL live band performances run the full dark LyricsMograph song slide in MANUAL mode — the right arrow lights the lyrics word by word and never starts a song ("the band performances, uses the right arrow to control the lyrics, not play the song"). Never wire an `audio` prop for a band act even when a track file is available — the user caught and reversed Lunar6tactics' backing-track wiring. Audio-tracked lyric slides are only for non-band acts that actually supply a track (Raien·Ditto, Kylie·Flashlight, the duet). Confidence: 0.9
- Song-slide intro/secondary text must be pure white (`text-ice`), not opacity-dimmed grey (`text-ice/70`, `text-ice/90`) — explicit request "change the intro text for all song slides to be white, not grey"; applied to the LyricsMograph artist line and performer credits. Confidence: 0.8
- Unconfirmed show content (TBC song titles, artists, TTML paths) is wired as live-editable `content` fields via /editor with explicit "Song TBC" notes, rather than hardcoded placeholder guesses — the operator can finalize details without a code change. Confidence: 0.6
- /editor-editable TBC fields are a last-resort fallback, never the deliverable. Confidence: 0.8
- Emphatic caps-word demands ("FULLY MUTE THE SLIDES") mean ABSOLUTE enforcement — implement defense-in-depth, not a single guard: layered redundant mechanisms (e.g., the existing MuteProvider PLUS a document-level capture-phase listener that mutes/zeroes/pauses any media element attempting playback, so even off-slide players like the end-credits BGM can never emit sound). Confidence: 0.7
- Console/monitor pages must scroll naturally at the page level — no `h-screen overflow-hidden` shells and no per-column `overflow-y-auto` traps; use `min-h-screen` and let columns grow with the page so nothing is cut off ("Enable scrolling in the controller page also"). Confidence: 0.7
- Slide-internal interactions must update on EVERY client, not just the stage: `advance` events execute the slide action (award-recipient reveals, lyric word-steps, game answer stamps) on each client's own slide instance via the shared store, event-id deduped so nothing double-fires — the controller's program monitor stays in lockstep with the hall ("make sure that the Interactions ... update on the Controller View, the stage Page is okk"). Confidence: 0.8
- Dark full-bleed engines mounted inside SlideShell's `page-light` scope must re-pin the `--color-ice` token (to `#eeeded`) at their own root — the scope flips ice to warm black, which silently darkened ALL text on the dark lyric slides and caused repeated "text colour" complaints. LyricsMograph does this; any future dark engine should too. Confidence: 0.8
- When an act's song changes to one that already has a synced slide, remap that slide's existing assets (audio / TTML / cover / sections) instead of building new ones ("lunar6tactics is playing still into you, i know i have the slide already made"). Confidence: 0.6
- When show content changes (song mappings, performers, credits), sweep every surface that encodes it in one pass — the slide file itself, the end-credits performer list in MovieCredits, and HANDOFF.md — so the deck stays internally consistent with the script. Confidence: 0.6
- Slide interactions must SATURATE at their end state — never wrap or cycle back to the start: advancing past the final lyric line has to hold on the fully-lit last line, not snap back to the song's intro card ("At the last verse, i click one more arrow, it leads me back to the intro"). Only the show cue moves the deck on; every step-based interaction (word reveals, "next line", countdown beats) should end by holding, not looping. Confidence: 0.85
- The dual-monitor setup has a GPU budget — lag complaints on the lyric engine are real and must be engineered away, not tolerated: right-size oversized layers to only what camera motion actually needs (oversize %, not blanket huge insets), cut blur cost (blur scales with layer area), and let the muted /controller monitor skip cinematic motion entirely (static camera, no shake/drift) since it's just a reference view — the stage keeps the full cinematic motion. User explicitly confirmed this approach resolved the lag ("my dedicated gpu in clutch, its not laggy at all nicee"). Confidence: 0.8

Confidence: 0.75
